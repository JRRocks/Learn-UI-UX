1. LA DEMANDE D’ORIGINE
======================================================================
« Crée-moi une application qui a pour but de devenir meilleur en UI/UX. Utilise les
ressources d’impeccable (https://github.com/pbakaus/impeccable) pour créer entièrement
tous les onglets et les ressources d’entraînement. Plusieurs systèmes d’entraînement
(sélectionner un visuel, texte explicatif, choix recommandé, le pourquoi, etc.).
Inspire-toi aussi d’Internet sur l’UI/UX. Mets en place des règles UI selon les pays
(l’UI occidentale diffère de l’UI chinoise), avec des entraînements sur les différences
et la façon de s’adapter. »

Règles de la session :
- Dépôt principal : JRRocks/Learn-UI-UX ; dépôt annexe : JRRocks/Library.
- Travailler, commiter et pousser UNIQUEMENT sur la branche claude/charming-bell-vrm1id
  (dans les deux dépôts) : git push -u origin claude/charming-bell-vrm1id
  (en cas d’erreur réseau : jusqu’à 4 essais avec attente 2 s, 4 s, 8 s, 16 s).
- Ne PAS ouvrir de pull request sans demande explicite.
- Terminer chaque message de commit par les lignes d’attribution que demande la session.
- Ne jamais écrire de nom de modèle dans le code, les fichiers ou les commits (hors
  lignes d’attribution imposées).
- Un hook d’arrêt exige un arbre de travail propre et poussé à chaque fin de tour : pour
  le contenu en cours d’édition par des agents, utiliser docs/reprise/outils/checkpoint.sh
  (ne commite un fichier que s’il passe le typage et la validation).
- Mode « ultracode » activé par l’utilisateur : orchestrer le travail substantiel avec
  l’outil Workflow (relecture adverse, vérification, réparation).

2. CE QUI EST FAIT (tout est poussé sur claude/charming-bell-vrm1id)
======================================================================
Application complète (Vite 8, React 19, TypeScript, vitest) :
- Moteur (src/engine) : 8 formats d’épreuves (choice, multi, truefalse, hotspot, order,
  match, slider, grid) + duels visuels, correction avec crédit partiel, boîtes de Leitner,
  SM-2 pour les fiches, XP, séries, maîtrise, badges, records, constructeur de sessions
  (jour, leçon, format, révisions, erreurs, examen, culture).
- Pages : Accueil, Apprendre (sommaire), Leçon, S’entraîner, Session, Défi chrono,
  Fiches, Cultures (12 profils de marchés, 8 comparaisons, labo de localisation),
  Ressources (catalogue des 62 règles du détecteur, aide-mémoire, glossaire),
  Progression, À propos. Thème clair/sombre, PWA hors ligne, CI GitHub Actions,
  déploiement GitHub Pages (déclenché sur main).
- Contenu : 24 leçons (≈ 410 épreuves, ≈ 320 fiches), profils et paires culturels,
  catalogue. Validation automatique (src/content/validate.ts, npm run validate).
- Outils d’auteur : npm run shots -- <module> [--mobile] [--dark] (captures) ;
  npm run check:mocks [-- <ids>] (textes coupés, superposés, < 11 px, contraste < 4,5:1,
  bureau 1180 px et mobile 390 px ; animations figées avant mesure).
- Kit des maquettes (src/components/mockKit.ts) : bordures de champs, cases et
  interrupteurs à 3,33:1, onglets à 11 px (plancher enseigné par les leçons).
- Typographie (src/lib/markdown.tsx, frenchSpacing) : espaces insécables françaises,
  plages « 36–40 » insécables (U+2060), nombres collés à leur unité, code court
  (≤ 20 caractères) insécable.
- Dépôt Library : moteur réutilisable moteur-entrainement/ (avec setRecord) poussé.

Relecture adverse du contenu (relecture → contradicteur-correcteur), TERMINÉE pour :
typography, color, layout, motion, delight, heuristics, personas, accessibility, process,
ux-writing, responsive, platforms, performance, laws, cognitive-load, dark-patterns,
polish, intensity, harden, onboarding, craft-floor, antipatterns (module), culture,
cultures (profils + paires). Environ 20 corrections par cible, toutes commitées.

Audit de l’application (5 dimensions, chaque constat reproduit puis vérifié par un
contradicteur) : 94 constats CONFIRMÉS (logique 27, accessibilité 22, design 26,
textes 19) ; 7 constats de performance trouvés, vérification en cours au moment de
l’arrêt.

C. Vague 2 — performance (après fusion de la vague 1)
   Vérifier puis corriger docs/reprise/app-vague2-performance.json :
   - perf-1 (P1) : tout le contenu (≈ 1,57 Mo, 475 Ko gzip) est chargé à l’ouverture de
     chaque page. Créer un index léger (métadonnées des modules + liste des épreuves
     id/type/difficulté/culture, fiches) et charger chaque module à la demande

   - perf-2 : feuille du kit recopiée dans chaque Shadow DOM → CSSStyleSheet partagée

   - delivery-1, logic-14 : chargement paresseux en échec → message et bouton Réessayer.

D. Passe de cohérence du contenu (après A, en workflow)
   - VRAI/FAUX : 57 épreuves, seulement 7 « Vrai » (culture est à 4/4). On gagne en
     répondant toujours « Faux » (Défi chrono compris). Viser ≈ 50 % : dans chaque
     module, transformer environ la moitié des vrai/faux en affirmations VRAIES,
     contre-intuitives mais exactes, en réécrivant explication et « À retenir »
     (outils/tf.mjs mesure l’équilibre). Le Défi chrono peut aussi tirer des vrai/faux
     équilibrés.

   - Terminer par npm run check:mocks (tout le contenu) et npm run validate.

6. LEÇONS APPRISES SUR L’ORCHESTRATION
======================================================================
- La limite d’usage a déjà interrompu le travail une fois : garder au plus 8 agents en
  parallèle ; un workflow plafonne à 2 agents simultanés (4 processeurs).
- Une reprise de workflow (resumeFromRunId) ne rejoue depuis le cache que le plus long
  préfixe inchangé d’appels agent() : après un échec, les agents suivants repartent.
- Les correcteurs de contenu travaillent dans le dépôt principal ; les correcteurs de
  l’app doivent travailler dans des worktrees git séparés (node_modules en lien
  symbolique) pour ne pas se gêner, puis on fusionne.
- Les agents posent parfois des captures à la racine du dépôt : /*.png est ignoré.
